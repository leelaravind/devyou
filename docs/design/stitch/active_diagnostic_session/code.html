science What to test

We need to verify if the local D1 instance is locking up when multiple write operations hit it simultaneously. The script below will spawn 5 concurrent `INSERT` statements against the local database.

Execute in Terminal
npx concurrently \ "wrangler d1 execute MY_DB --local --command='INSERT INTO test (id) VALUES (1)'" \ "wrangler d1 execute MY_DB --local --command='INSERT INTO test (id) VALUES (2)'" \ "wrangler d1 execute MY_DB --local --command='INSERT INTO test (id) VALUES (3)'"

Expected Result

[0] Executing on local database MY_DB (path/to/db) [1] Executing on local database MY_DB (path/to/db) [2] Executing on local database MY_DB (path/to/db) [0] ┌──────────────────────────┐ [0] │ changes: 1, duration: 2ms│ [0] └──────────────────────────┘ ... (all 3 should succeed without SQLITE_BUSY)
warning

Potentially Destructive Next Step

If this fails, the next playbook node involves running `wrangler d1 migrations apply --local`, which may reset local state depending on your schema setup.

Why this test matters expand_more
D1 uses SQLite under the hood. Local environments often default to journal_mode=DELETE rather than WAL, making concurrent writes highly susceptible to SQLITE_BUSY locks.
